# Releasing the `@stellaragent` npm packages

This document describes how the three TypeScript packages are versioned and
published:

- `@stellaragent/core` — [`packages/core`](packages/core)
- `@stellaragent/cli` — [`packages/cli`](packages/cli)
- `@stellaragent/react` — [`packages/react`](packages/react)

## Versioning strategy: independent

The packages version **independently** (Changesets default). They are NOT locked
to a single shared version.

- A change to `@stellaragent/core` bumps only core. Because `@stellaragent/cli`
  and `@stellaragent/react` depend on core via `workspace:*`, their internal
  dependency reference is bumped too (`updateInternalDependencies: always` in
  `.changeset/config.json`), but their own public version only moves when they
  have a changeset of their own.
- Each package releases on its own cadence. Consumers can adopt whichever
  packages they need without pulling in unrelated bumps.

The first release (`0.1.0-alpha.0`) publishes all three packages together
simply because none have been published yet.

## Tooling

- [Changesets](https://github.com/changesets/changesets) — version bumps and
  changelog generation. Configured in `.changeset/config.json`; the GitHub-flavored
  changelog is generated by `@changesets/changelog-github`.
- [`.github/workflows/release.yml`](.github/workflows/release.yml) — tag-triggered
  release workflow that builds every package and publishes to npm.

## Cutting a release

1. **Add a changeset** on a feature branch:

   ```md
   ---
   '@stellaragent/core': minor
   '@stellaragent/cli': patch
   ---

   Add `payForAPI` to the SDK and expose it through the CLI.
   ```

   Bump levels: `patch` / `minor` / `major`. Prereleases use the `tag` field,
   e.g. `tag: alpha` produces `0.1.0-alpha.0`.

2. **Version.** A maintainer runs:

   ```bash
   pnpm changeset version
   ```

   This bumps the affected `package.json` files, writes the changelog, and
   removes the consumed changeset files. Commit the result on `main`.

3. **Tag.** Once the version PR is merged:

   ```bash
   git tag v0.1.0-alpha.0   # version must match package.json
   git push --tags
   ```

   The tag prefix `v*` is namespaced so it cannot collide with the Python SDK
   (`sdk-python-v*`) or Rust SDK (`sdk-rust-v*`) tags used by the other release
   workflows.

4. **Publish.** The tag push triggers
   `.github/workflows/release.yml`, which:
   - installs dependencies,
   - verifies the tag matches `packages/core/package.json`,
   - builds `@stellaragent/core`, `@stellaragent/cli`, and `@stellaragent/react`,
   - runs `pnpm changeset publish`, which publishes every package whose version
     is not yet on npm.

   Publishing requires an `NPM_TOKEN` repository secret
   (Settings → Secrets and variables → Actions). Without it, the workflow skips
   the publish step and reports that the secret is missing.

## npm provenance

npm attaches [provenance](https://github.com/npm/cli/blob/latest/docs/content/provenance.md)
automatically to every authenticated publish (npm CLI ≥ 7). Each published
version therefore carries cryptographic proof that it was built and published
from this repository — no extra flags are required in the workflow.

## First alpha (proof of pipeline)

A first alpha is staged in `.changeset/alpha.md` and bumps all three packages
from `0.1.0` to `0.1.0-alpha.0` with `tag: alpha`. To publish it:

```bash
pnpm changeset version          # bumps to 0.1.0-alpha.0, writes changelog
git commit -am "release: 0.1.0-alpha.0"
git tag v0.1.0-alpha.0
git push --tags                 # triggers release.yml → npm publish with provenance
```

Until `NPM_TOKEN` is configured in the repository, the publish step is skipped
with a clear message; everything up to and including the build is verified by
the workflow.
